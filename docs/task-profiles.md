# Task profiles

Lens groups an agent's runs into tasks with a decision model through your LiteLLM gateway. Nothing is grouped until a proxy admin sets up **Task discovery** on the Profiles page, described under [Enhanced discovery](#enhanced-discovery). Until then the Profiles tab shows runs as `Not configured` and says what to set up: a decision model on the gateway when it has none, otherwise a discovery under **Task discovery**. Recorded `task_category` or `scenario` values always take precedence and need no setup

Callers who cannot read every team never see the shared categories, so their runs without a recorded category show as `Unclassified`

## Profiles view

The Profiles tab shows one agent's runs in the selected time range as a breakdown ranked by runs or spend, an optional similarity map, and a heatmap of profiles against model deployments. Each profile keeps the same color in every view, and placeholder profiles such as Unknown and Pending stay neutral. The similarity map draws only runs whose position came from discovery embeddings and labels each group directly, in the style of Nomic Atlas data maps (https://docs.nomic.ai/atlas/datasets/data-maps) and DataMapPlot (https://datamapplot.readthedocs.io/en/latest/basic_usage.html). Beside the map, each category appears once with its total runs and how many of them are shown on the map, such as `9 runs, 6 shown on map`. Recorded categories and runs classified after discovery have no position, so they show fewer or zero runs on the map instead of invented positions. Placeholders such as Unknown are labelled as not mapped, which keeps an unknown assignment distinct from a missing position. The breakdown follows the concept overview in LLooM's visualization guide (https://stanfordhci.github.io/lloom/about/vis-guide.html). Each run is counted once and keeps one profile. A recorded `task_category` or `scenario` always wins. Otherwise a run takes the agent's discovered category when active categories exist, and shows as `Not configured` when they do not. Runs that started before the categories were activated and were not backfilled stay `Unclassified`

Requests are the agent's own model calls inside those runs. Lens resolves them with the same strict ledger matching the trace view uses, so a call counts once even when it was exported twice, and calls that share a ledger record are one request. A request that other agents in the same run also exported is counted as shared and charged to neither agent. Cost is known only when every ledger record behind a request is priced. Otherwise the view says how many requests the spend rests on and never shows the missing part as zero. Retries charge the whole request. When the attempts used different deployments, the request appears under `multiple deployments` instead of being priced as either one. The gateway's compact cost records have no delivery identity, so the view does not report deliveries

Heatmap columns are gateway deployment IDs recorded on the ledger. Ledger records without one appear under their model group, records written before Lens stored deployment metadata appear under `unknown`, and calls without a matching record appear as unmatched. Callers who can read every team also see configured deployments without traffic. The heatmap shows requests, average cost and p95 latency only. It does not judge whether a model suits a category, and evaluation results are not collected yet

Selecting a profile opens a drawer with its description, per-model requests, cost and latency, and its recent runs, each of which opens its trace. A run whose spans could not be read shows its requests and spend as unavailable, and model figures that cover only part of the runs are labelled as partial instead of as zero. **Investigate these runs** opens a new investigation with the agent, profile and lookback already selected. It does not start the investigation

Each request reads at most 5,000 runs and 50,000 spans. When a range holds more, the view labels the figures as partial and shows how many runs they cover

## Enhanced discovery

Enhanced discovery is optional and makes model calls through your LiteLLM gateway. It does nothing for an agent until a proxy admin saves models and starts a discovery under **Task discovery** on the Profiles page. Opening that panel, counting eligible runs or saving models never calls a model. Its names and examples come from every team's runs, so only proxy admins can change settings, start a discovery, or start, pause and resume classification. Other callers see the panel read-only when categories exist

The panel takes three models from the gateway configured by `LENS_GATEWAY_API_BASE` and `LENS_GATEWAY_API_KEY`. The discovery model is a chat model that writes a one-line intent for each sampled request and then names each group. The embedding model is a gateway model reported with `mode: embedding`. The decision model assigns each run to a category, and must be `typesafe` or a gateway model reported with `mode: decisions` (or the legacy `mode: evaluation`). The pickers only list models the gateway reports for each role, and saving refuses an alias that is not in that list. `LENS_PROFILE_DISCOVERY_MODEL`, `LENS_PROFILE_EMBEDDING_MODEL` and `LENS_PROFILE_CLASSIFICATION_MODEL` only prefill the pickers. Lens reads the gateway's models at startup, so after changing the gateway config, or when Lens started before the gateway was ready, use **Refresh models** in the panel or in **Settings** as described in [Signals](signals.md#connect-a-litellm-gateway). Set `LENS_GATEWAY_URL` and `LENS_GATEWAY_SECRET` too, so these calls are signed as internal Lens traffic and keep their tags on the gateway

Models can be saved before an agent has enough runs. To discover categories, pick a date range and a sample size between 20 and 500 (300 by default). The panel counts the eligible runs in that range, for example `1 of 20 eligible runs collected`, and **Discover categories** stays unavailable until the range holds at least 20. **Refresh count** counts again without calling a model, and the server and worker both check the minimum again. Eligible runs are this agent's runs without a recorded category and with a request, counted once per team, key and trace, that are still inside the configured trace retention (`AGENT_TRACING_RETENTION_DAYS`), and discovery reads the most recent ones up to the sample size. A range reaching further back than retention only counts the runs still kept, and classification also skips runs past retention, so an expiring run is never paid for twice. Starting a discovery shows the range, sample and models before any call is made, and those models are stored with the job, so later settings changes do not alter it. **Cancel discovery** discards a running discovery without touching active categories

Discovery follows LLooM's concept induction (Lam et al., CHI 2024, https://arxiv.org/abs/2404.12259, https://github.com/michelle123lam/lloom). It reads up to 500 recent unrecorded runs of the agent and distills each into a one-line intent so domain vocabulary does not drive the groups. It embeds the intents (Qwen3 embeddings, https://github.com/QwenLM/Qwen3-Embedding), reduces them with UMAP tuned for density and clusters them with HDBSCAN, as the UMAP clustering guide advises (https://umap-learn.readthedocs.io/en/latest/clustering.html, https://scikit-learn.org/stable/modules/generated/sklearn.cluster.HDBSCAN.html). The Rust ports are `umap-rs` and `hdbscan`. A separate two-dimensional UMAP places the discovery sample on the map. That layout comes from one stochastic run and is stored, not recomputed. Runs added later have no position. A model then names each of the twelve largest groups and writes a description and the criteria the decision model uses to classify runs

When discovery finishes, the panel lists the discovered categories with their descriptions. Categories cannot be edited in this revision. **Start classifying new runs** activates them for runs that start from then on, and an unchecked option also classifies the discovery range and shows how many runs that covers. Older runs outside those ranges stay `Unclassified`. Each run is compared with the active definitions, and a companion question asks whether it fits any of them at all. A run that fits no definition becomes `Unknown`. A run without a request preview has nothing to compare, so it also becomes `Unknown` without a model call. Runs are matched by when they started, and each run is classified once per active version. Classification works in batches of 20 under a lease shared by replicas, and a run that fails three times is left pending

Once categories are active, the panel shows whether classification is running, when the categories were discovered and from how many runs. **Pause classification** stops classifying new runs and also cancels a running discovery, keeping existing results. Runs that start while it is paused stay `Unclassified`. **Resume classification** starts it again for new runs. **Rediscover categories** starts a new manual discovery with its own range and sample. New runs never trigger a rediscovery, and the active categories keep classifying until an admin explicitly starts classifying with the replacement. Replacing categories starts a new generation, so assignments from an earlier one never come back

This adaptation keeps LLooM's distill, cluster and synthesize steps but scores runs with a decision model instead of a generative judge, and limits a discovery to one agent and 500 runs. Grouping quality has not been measured against human labels
