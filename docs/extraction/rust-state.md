# Rust application-state storage

The application-state store is now available in `litellm-storage-clickhouse::state`, following the storage boundary in the Rust migration specification. This is a foundation for porting the control plane. The running Python application has not been switched to Rust, and none of the full-product completion requirements is closed by this change

The port is based on `src/litellm_lens/clickhouse_state.py` at Lens commit `37276a43`, fetched from main before work began. It keeps the same `lens_state_heads` KeeperMap table and `lens_state_blobs` ReplacingMergeTree table. A prepared commit inserts immutable JSON payloads first. Publication changes their small heads together with strict KeeperMap version checks, with internal Keeper retries disabled. Failed or losing preparations cannot make their payloads visible through normal reads

`ClickHouseState` accepts the existing shared HTTP client and a connection selecting the application database. `initialize` creates the two generic state tables. `read`, `read_many` and `resolve` return snapshots containing a key, revision, digest and JSON value. `prepare` and `publish` expose the two publication phases; `commit` performs both. `update` retries revision conflicts while leaving transport and storage failures visible to its caller. Callers must reread after an ambiguous publication response rather than assuming it failed

Historical reads use the complete key/revision/digest identity, including when two requested snapshots have the same key. New reads verify payload hashes before decoding them. Missing published payloads return an unavailable error, never an empty record. Null tombstones retain their revisions so stale writers cannot resurrect deleted records

The fixtures under `runtime/crates/storage-clickhouse/tests/state/fixtures/python_payloads.json` were produced with the unchanged Python `next_blob` function from that Lens commit. Rust tests insert those exact rows, read them, publish a later revision, and resolve the original revision. They cover floats with Python's exponent formatting, Unicode, escaped characters, nested values and tombstones. The reader hashes stored bytes directly; it does not require old JSON to use Rust's formatting

The Rust transport has a 64 MiB limit for an encoded commit body and a response body. The boundary tests accept exactly that limit and reject a larger body. This is a new explicit bound compared with the unbounded Python helper. Full-product large-record and capacity qualification remains open. The port also rejects invalid head metadata, duplicate rows and corrupt payloads rather than using them as valid state

Domain-specific schedule, job and worker materialized views still belong to the existing application initializer. Port those schemas with their repositories before replacing that initializer. HTTP authentication and dataset fixture replay, the remaining domain ports, Rust contract ownership, provider-backed analysis, and removal of the Python backend remain unfinished

Run the storage cases from the current Rust workspace with `CLICKHOUSE_STATE_TEST_URL=http://127.0.0.1:18124 cargo test -p litellm-storage-clickhouse --test state --test state_transport`. Without that environment variable, each database fixture starts a pinned test-owned ClickHouse container with Keeper. The restart case always owns its container, forcibly stops it, waits for ClickHouse and Keeper to recover, and verifies committed values, unpublished values and stale-write fencing. It never restarts a developer's existing ClickHouse container

The tests distinguish storage-layer evidence from product qualification. They do not prove a populated PostgreSQL migration, backup/restore, garbage collection, a multi-node installation, an investigation using a real provider, or standalone/embedded UI parity

Validation used Rust 1.99.0 and ClickHouse 26.9.6.6. The final storage suite has 48 cases, including live persistence and concurrency cases, Python payload replay, protocol failures and body limits. Workspace Clippy passes with warnings denied. The [restart log](evidence/rust-state-restart.log) records the forced-stop rehearsal and the [Clippy log](evidence/rust-state-clippy.log) records lint validation

The [mutation report](evidence/rust-state-mutations.json) combines two cargo-mutants 27.1.0 runs over the new state implementation. Of 90 generated mutants, 14 do not compile, 70 are caught, and 6 survive, giving a 92.1% kill rate among viable mutants. The survivors change retry-delay arithmetic; they remain listed and are not counted as caught. The first run exposed untested size boundaries; the added boundary cases caught all five of those mutations in the second run. Both [initial](evidence/rust-state-mutants-initial.log) and [follow-up](evidence/rust-state-mutants-followup.log) logs are retained. The tool exits nonzero because timing mutants survive
