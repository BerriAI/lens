# Rust authentication and sessions

Authentication now has a Rust implementation in Ishaan's layout, based on Lens main at `8d3ee87a`. The contract crate owns the authentication wire types, the auth crate owns identity and session policy through a repository trait, the ClickHouse storage crate implements that trait, and the server crate serves `/auth/session`. The existing Rust binary wires them together when `LENS_ADMIN_TOKEN` is present

The port preserves setup-token login, hashed session identifiers, eight-hour expiry, cookie attributes, revocation, bearer precedence, origin checks on cookie writes, and short-lived signed LiteLLM identities. Delegated identities retain the seven existing roles and authorized trace teams. No database other than ClickHouse and its Keeper is used by this implementation

Sessions use the same encoded keys, `lens_state_heads` and `lens_state_blobs` as the Python application. Independent clients read existing timestamp representations, duplicate session creation conflicts, and revocation leaves a tombstone. The setup token and raw session cookie are never stored in the session record. Storage failures remain distinct from an absent or expired session

Set `LENS_ADMIN_TOKEN` to a secret with at least 32 characters and `LENS_PUBLIC_URL` to the browser-facing HTTP(S) origin. `LENS_GATEWAY_SECRET` optionally enables delegated identities. These configure the new auth routes on the worker's existing listener. The current binary still needs its existing worker/control-plane configuration; enabling these routes does not make the complete Rust product standalone. Existing deployment definitions have not been switched to this partial API

The unchanged Python reference harness recorded 27 additional boundary fixtures. Together with the 18 existing auth fixtures, all 45 replay successfully against real Rust HTTP and ClickHouse. They cover login, logout, cookie expiry, origin denial, bearer syntax, gateway signature and claim validation, numeric date coercion, strict request fields, and content types. `cargo test -p lens-server --test sessions` runs these replays as part of the normal CI test job, with an actually expired stored session for the expiry case

The HTTP lifecycle cases also restart the Rust server, read the existing cookie through an independent connection, reject cross-origin logout, revoke it, restart again, and reject replay. A separate storage test forcibly stops and restarts a test-owned ClickHouse container both before and after revocation. Those tests never restart the developer's existing ClickHouse container

The actual `litellm-lens` binary was started on port 4321 with ClickHouse and an unavailable control-plane address. Its [27 boundary replays](evidence/rust-auth-binary-replay.log) passed. The [curl transcript](evidence/rust-auth-curl.log) records successful login and cookie lookup, denied cross-origin logout, successful logout, and rejection of the old cookie. This proves authentication does not need a running gateway or a model provider. It does not qualify investigation execution or overall readiness without the control plane

The [workspace run](evidence/rust-auth-workspace.log) passed 1,384 tests with four normally ignored cases. Five subsequent auth/error cases passed in the [focused run](evidence/rust-auth-unit.log), giving 1,389 distinct regular cases exercised for this increment. The [four normally ignored trace cases](evidence/rust-auth-live-traces.log) also passed against real Rust HTTP and ClickHouse. Formatting and [workspace Clippy](evidence/rust-auth-clippy.log) pass with warnings denied

The [auth mutation report](evidence/rust-auth-mutations.json) records 64 generated mutations, five unviable, 58 caught and one surviving, a 98.3% kill rate among viable mutations. The survivor changes a redundant issuer/audience check whose rejection is also enforced by the JWT library. The initial run identified an uncovered boolean numeric-date case; the added regression catches that mutation in the follow-up. The contract crate currently contains derived auth types and generates no executable mutants of its own. The [session-storage mutation report](evidence/rust-auth-storage-mutations.json) records six viable mutations, all caught, and five unviable mutations

Full replacement remains unfinished. Malformed JSON still reports Rust parser diagnostics instead of Python's exact diagnostics, multiple extra-field validation errors need ordering qualification, and Axum's default request-body limit differs from the previously unbounded Python handler. These are explicit parity gaps, so the Python auth modules and route inventory remain in place. The remaining worker contract still comes from the old generator; introducing auth types does not complete Rust contract ownership

The broader extraction plan remains unchanged. Standalone provider-backed investigations, the other API/domain ports, embedded identity and browser workflows, migration/recovery, capacity, releases, project-releaser, ops, charts and documentation still need their completion evidence. None of the 67 full-product acceptance requirements is closed by this increment

Before publication, the native eval SDK merged into main at `b27fdb70`. The auth increment was rebased onto it, preserving both sets of Cargo lockfile entries. The [combined workspace run](evidence/rust-auth-rebased-workspace.log) passed all 1,446 regular tests with four normally ignored cases, and [Clippy](evidence/rust-auth-rebased-clippy.log) and formatting passed. The source manifest still resolves every recorded destination
